# Accessibility Policy and Agent-Friendly Testing Research

**Research date:** 2026-10-02
**Status:** Research snapshot captured before the scope decision. The accepted decision is in [ADR 0016](../adr/0016-wcag-22-aa-accessibility-reference.md), the public scope statement is [`ACCESSIBILITY.md`](../../ACCESSIBILITY.md), and the incremental plan is [here](../plans/681-accessibility-rollout.md). This report remains evidence and source synthesis, not a conformance claim.

## Purpose and scope

This report consolidates the repository review and reference research on accessibility guidance for Obsidian plugins, along with the project's AI-assisted UI testing context. The agent-testing question is specifically about making the plugin easier to inspect and operate through visual control, browser automation, and Chrome DevTools Protocol (CDP) access.

The findings distinguish verified repository facts and source statements from recommendations or inferences. Absence findings are bounded to the files and searches named here; they are not proof that no relevant reference exists anywhere in every historical artifact.

## Recommendation

**A repository-wide accessibility document and a separate rollout plan are warranted.** This repo is not starting from zero: [the design spec already has explicit accessibility expectations](design-spec.md#L361-L380), and its UI testing section describes which checks belong in jsdom versus manual runtime inspection ([design spec](design-spec.md#L548-L566)). The need is to establish their project-wide scope, resolve old versus current declarations, and state how accessibility and AI-driven testing fit together.

The accepted follow-up creates a root `ACCESSIBILITY.md` for user-facing scope, known limitations, and feedback, plus an incremental plan under `docs/plans/`. The project chose WCAG 2.2 Level AA as a design and audit reference for applicable plugin-owned UI, without claiming current conformance. GitHub describes an accessibility page as a place for priorities, environments, known barriers, contributor expectations, reporting, ownership, and maintenance ([GitHub guidance](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-an-accessibility-page-to-your-repository)).

For rollout order, address clear severe barriers and improve shared controls and high-impact workflows incrementally. Use low current coverage as a risk signal and tie-breaker, not the only ordering rule. The accepted approach avoids a time-intensive coverage or usage study: make a lightweight pass over obvious barriers while improving the plugin generally. Candidate areas below remain hypotheses because no verified usage-frequency data was found.

## Verified findings in this repository

### Standards and stated expectations

- I found no explicit WCAG version/level, WAI-ARIA conformance target, or statement that the plugin conforms to an accessibility standard in the contributor/agent instructions or active design/testing documents searched. The active sources do make concrete implementation requirements, but do not tie them to a named success-criteria set. Search scope included `AGENTS.md`, `.instructions.md`, `CONTRIBUTING.md`, `docs/development/`, `eslint.config.mjs`, `package.json`, and relevant source/tests.
- The design spec says nav controls should have visible `:focus-visible` outlines, distinguish active states without hover, work on touch, preserve readable contrast in dark and light themes, give icon-only controls keyboard parity, and respect reduced-motion expectations ([design spec](design-spec.md#L361-L380)). It also defines a 32px minimum interactive hit area and prefers 40px for mobile modal controls and icon buttons.
- The design spec explicitly asks that active, destructive, and disabled states not rely on color alone when another signal is feasible; clickable icons must respond to Enter and Space; and loading controls should retain accessible labels ([design spec](design-spec.md#L373-L380)). The design review checklist calls out focus-visible and contrast ([design spec](design-spec.md#L389-L397)).
- The design spec's icon guidance currently distinguishes legacy controls from new work: it says new icon buttons should be native `<button type="button">` elements and that the older `div[role="button"]` pattern describes existing controls awaiting migration ([design spec](design-spec.md#L414-L447), [open question #502](design-spec.md#L570-L582)).
- The UI testing section explicitly acknowledges that jsdom does not lay out or paint. It directs unit tests to assert DOM structure, labels, roles, icons, and Enter/Space behavior, while layout, breakpoints, theme colors, focus rings, and mobile rendering are checked manually in the fixture vault ([design spec](design-spec.md#L548-L566)).

### Instructions, lint, and conflicts

- `.instructions.md` tells contributors to use Obsidian's `setTooltip()` or `aria-label`, and forbids the HTML `title` attribute because it creates a second or unthemed tooltip ([.instructions.md:19](../../.instructions.md#L19)). ESLint implements a targeted rule for `title` usage and requires the `attr` object to be inline so the rule can inspect it ([eslint.config.mjs:8-11](../../eslint.config.mjs#L8-L11), [eslint.config.mjs:102-132](../../eslint.config.mjs#L102-L132)). The rule is a tooltip convention; it is not a general accessible-name, keyboard, or WCAG checker.
- At the time of review there was an explicit conflict in the design spec's legacy instructions: existing custom icon controls were told to provide an `aria-label` **or `title`** ([design spec:414-434](design-spec.md#L414-L434)), while `.instructions.md` and ESLint prohibited `title`. The design spec has since been updated to make the legacy recipe migration-only and remove the `title` exception; the later native-button migration still follows [issue #502](https://github.com/amatya-aditya/obsidian-rss-dashboard/issues/502).
- The design spec recommends a native button for new work but retains a div-based recipe for existing controls. Source examples show both patterns. The shared toolbar helper builds a focusable `div` with role, tabindex, accessible name, click handling, and Enter/Space handlers ([`sidebar-icon-registry.ts:80-104`](../../src/utils/sidebar-icon-registry.ts#L80-L104)). In contrast, Reader header save/read/star actions are `div`s with `aria-label` and click handlers in the inspected section; neighboring tag and reader-settings actions add role, tabindex, and keyboard handlers ([`reader-view.ts:840-955`](../../src/views/reader-view.ts#L840-L955)). This is evidence of mixed patterns, not a complete audit of every control.

### Tests and enforcement

- Vitest includes unit tests under `test_files/unit/**` and uses jsdom ([`vitest.config.mjs:39-43`](../../vitest.config.mjs#L39-L43)). The package scripts expose lint and unit tests; dependencies include Vitest and jsdom, not a declared Playwright or axe package ([`package.json:20-54`](../../package.json#L20-L54)). The lockfile search found no `playwright`, `@playwright/test`, `axe-core`, or `@axe-core/playwright` package entry. The lockfile does contain Vitest's browser-Playwright integration package as part of Vitest's dependency graph; no repository script or config uses it as a browser test runner.
- There are focused unit tests that assert accessible names, roles, tabindex, and Enter/Space behavior. For example, the article empty-state test checks the custom settings action's role, label, tabindex, and keyboard activation ([`article-list-empty-state.test.ts:163-250`](../../test_files/unit/components/article-list-empty-state.test.ts#L163-L250)). Other tests cover individual keyboard helpers and selected ARIA states. This is useful regression coverage, but it does not establish consistent coverage across every modal, view, responsive state, theme, or plugin surface.
- ESLint and CI enforce the configured code rules and run the unit suite; CI's workflow steps show compliance checks, blocking lint, and Vitest with coverage ([`.github/workflows/test.yml:37-72`](../../.github/workflows/test.yml#L37-L72)). Nothing in the inspected CI workflow runs an automated accessibility scan, launches Obsidian for accessibility checks, or performs keyboard/screen-reader verification.
- The design spec correctly documents the current test boundary: jsdom assertions cover markup and event behavior, while visual/runtime properties need rendered UI and manual inspection ([design spec:548-566](design-spec.md#L548-L566)). Automated semantic checks and screenshot review would complement these tests, not prove complete accessibility.

### Browser and agent testing context

- An existing performance plan proposes launching Obsidian with `--remote-debugging-port` and driving CDP from Node, but that track is explicitly deferred and measures runtime performance ([performance plan:195-212](../plans/370-performance-program.md#L195-L212)).
- An archived E2E research document preferred `wdio-obsidian-service` over a hand-built Playwright/Puppeteer-over-CDP harness because of Obsidian setup and sandboxing work; that was a recommendation about adopting an E2E runner at the time, not an accessibility standard ([E2E research:29-52](../archive/investigations/2026/obsidian-e2e-research.md#L29-L52)). It also records Vitest as unit/jsdom-only. The current task context adds that AI testing can already use visual control/screenshots and port/CDP access; that current capability is user-provided context, not something established by those archived repository documents.
- **Inference:** the most useful automation contract is likely the UI's real semantic role/name/state and keyboard behavior, readable through the accessibility tree, with screenshots for visual state. The repository's earlier CDP notes do not yet define such an accessibility-oriented test workflow.

### Follow-up source pass on the selected base

On 2026-10-02, I reviewed `origin/dev` at commit [`03c127e`](https://github.com/amatya-aditya/obsidian-rss-dashboard/commit/03c127e59082989e3dbc815714c984a55ca155b0). This was a static source and test review, not a running-plugin keyboard, screenshot, or screen-reader audit.

- **Verified keyboard barrier:** the article-header hamburger, themed select triggers, and menu options use click handlers on custom `div` elements. The triggers use `role="button"` and `tabindex="0"`, but `article-header-menu.ts` contains no keyboard handler; the popup options are plain clickable `div` elements. The component tests exercise clicks but have no keyboard assertions. This makes the menu's sort, filter, grouping, view, and card-layout controls unavailable through its keyboard path. Relevant references are [WCAG 2.1.1 Keyboard (A)](https://www.w3.org/TR/WCAG22/#keyboard) and [4.1.2 Name, Role, Value (A)](https://www.w3.org/TR/WCAG22/#name-role-value). See the [trigger implementation at the audited commit](https://github.com/amatya-aditya/obsidian-rss-dashboard/blob/03c127e59082989e3dbc815714c984a55ca155b0/src/components/article-header-menu.ts#L54-L76), [the options](https://github.com/amatya-aditya/obsidian-rss-dashboard/blob/03c127e59082989e3dbc815714c984a55ca155b0/src/components/article-header-menu.ts#L407-L449), and [component tests](https://github.com/amatya-aditya/obsidian-rss-dashboard/blob/03c127e59082989e3dbc815714c984a55ca155b0/test_files/unit/components/article-header-menu.test.ts#L52-L200).
- **Focus needs rendered review:** inspected search-input and themed-select rules suppress the browser outline and use a border color as the focus change. Other controls use a box shadow or explicit outline. Static CSS inspection cannot establish whether these indicators remain visible across themes and surfaces; verify rendered states against [WCAG 2.4.7 Focus Visible (AA)](https://www.w3.org/TR/WCAG22/#focus-visible). Evidence: [search rules](https://github.com/amatya-aditya/obsidian-rss-dashboard/blob/03c127e59082989e3dbc815714c984a55ca155b0/src/styles/controls.css#L64-L67) and [themed-select rules](https://github.com/amatya-aditya/obsidian-rss-dashboard/blob/03c127e59082989e3dbc815714c984a55b0/src/styles/controls-dropdown.css#L405-L409).
- **Verified test boundary:** the unit suite has component-level tests for some labels, states, and keyboard behavior, but the repository does not configure a CDP accessibility-tree or browser audit runner. The testing guide describes jsdom DOM tests; the design spec reserves visual focus and rendered theme checks for manual verification. This is a gap in systematic coverage, not evidence that a standalone browser runner is required.
- **Recommendation:** track implementation changes with the applicable WCAG success criterion or criteria and any stricter project baseline. Treat each citation as a traceable rationale and focused acceptance check, not as a claim that one fix establishes conformance.

## External references

### Standards and Obsidian platform references

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the normative standard text. The [WAI-ARIA Authoring Practices Guide introduction](https://www.w3.org/WAI/ARIA/apg/about/introduction/) explains that the APG is informative implementation guidance rather than a conformance standard; its [keyboard interface practices](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) give concrete patterns for keyboard operation and focus management.
- Obsidian's [developer documentation](https://docs.obsidian.md/) provides plugin and UI API guidance, but I did not find a platform-wide community-plugin accessibility conformance target there during the review. Its settings documentation notes that long setting descriptions can hinder scanning and may not be guaranteed to be read ([Settings UI documentation](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/User%20interface/Settings.md)). Treat this as a product-writing constraint, not a substitute for accessibility criteria.

### Obsidian plugin examples

- **Best complex-plugin reference: [Extended Properties](https://github.com/electroluminescent/obsidian-extended-properties).** The repository contains a dedicated [`ACCESSIBILITY.md`](https://github.com/electroluminescent/obsidian-extended-properties/blob/main/ACCESSIBILITY.md), and its README links to it as the full support summary. The README describes keyboard paths, screen-reader labels, focus-visible rings, Escape behavior, live announcements, forced-colors support, and reduced motion. GitHub's text fetch for the document itself was unavailable during this review, so those details are verified from the README summary and the document's existence, not a direct reading of every statement inside the accessibility file.
- **Best short scope example: [Note Toolbar's Accessibility page](https://github.com/chrisgurney/obsidian-note-toolbar/wiki/Accessibility).** It separately describes keyboard navigation, high-contrast color customization, accessible item labels, and how users can report accessibility issues. It is practical and plugin-scoped but does not state a WCAG target.
- **Best standards/audit structure example: [Obsidian A11y Enhancer](https://github.com/KnobeDev/obsidian-a11y).** It names WCAG 2.1 AA, maps audited UI areas to success criteria, and documents limitations that the plugin cannot fix upstream. Its scope is retrofitting Obsidian's core interface at runtime, so copy its standards mapping and limitations format, not its scope claim.
- Kepano's [Minimal Theme Settings repository](https://github.com/kepano/obsidian-minimal-settings), including its contributor/agent docs, and [Minimal Theme](https://github.com/kepano/obsidian-minimal) offer useful examples for UI configuration, theme integration, and manual checks. In the reviewed pages I found no dedicated accessibility scope document or declared WCAG target; they are supporting UI references, not the best accessibility-policy model. [Advanced Appearance](https://github.com/kepano/obsidian-advanced-appearance) is archived/retired and is historical context only.

### Automated testing and agent navigation

- [Playwright best practices](https://playwright.dev/docs/best-practices) says to test user-visible behavior, isolate tests, and prefer user-facing attributes or explicit contracts over selectors coupled to CSS/DOM structure. Its [locator guidance](https://playwright.dev/docs/locators) prioritizes role plus accessible name, label, visible text, and then explicit test IDs where useful. It says role locators do not replace accessibility audits or conformance tests.
- [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing) demonstrates running axe scans inside tests and scanning a state after interactions reveal a menu or other content. Playwright explicitly warns that automation cannot detect every WCAG violation.
- Anthropic's [Browser Use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool) explain a dual interface: agents can read the accessibility tree and act on returned element references, or use screenshots and coordinates. The docs recommend semantic references when available because they survive layout/reflow and can target controls that are difficult to click; screenshots remain useful for visual layout and rendering. The page also notes references can become stale after navigation or material DOM changes.
- Anthropic's [computer and browser use best practices](https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude) says small targets reduce click accuracy, and suggests larger targets or keyboard alternatives; it also discusses image scaling and screenshot-coordinate alignment. These are direct tips for visual agent reliability.
- The [Chrome DevTools accessibility reference](https://developer.chrome.com/docs/devtools/accessibility/reference) describes inspecting the accessibility tree and computed properties. Chrome emphasizes that automated inspection can help with markup, but keyboard and screen-reader navigation still require direct use. The [CDP Accessibility domain](https://chromedevtools.github.io/devtools-protocol/tot/Accessibility/) exposes full/partial accessibility-tree queries and AX node data that a CDP-based harness can inspect.
- OpenAI's [Computer Use guide](https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use) is principally about the agent harness: computer use is intended for interacting with and testing applications through a browser UI, and it documents session activity and screenshot review. It is less prescriptive than Playwright or Anthropic about what semantics an app should expose. OpenAI's [Apps SDK UI guidance](https://developers.openai.com/plugins/concepts/ui-guidelines) does name WCAG AA contrast, alt text, text resizing, and accessible components, but it governs ChatGPT app surfaces specifically and should not be treated as a general Obsidian plugin standard.
- [WebMCP](https://developer.chrome.com/docs/ai/webmcp/) and the [W3C Web Machine Learning Community Group explainer](https://github.com/webmachinelearning/webmcp) propose structured, discoverable actions for browser agents instead of brittle screenshot/DOM actuation. This is an emerging proposal/early-preview path, not a current Obsidian-plugin requirement. The proposal explicitly says WebMCP does not replace or directly expose the page's accessibility tree; it is a separate machine-action interface.

## Synthesis for this repository

### What guidance overlaps

- Native semantic controls, accessible names, keyboard operation, and visible focus help both people using assistive technology and automation that queries roles, names, and states. Playwright and Anthropic describe this from the test/agent side; the repository design spec and existing tests already use these concepts.
- Human-facing automation and visual checking are complementary. Role/name/keyboard checks can robustly exercise controls; screenshots can verify focus styling, contrast, clipping, responsive layout, and visual states that a DOM tree cannot establish.
- Existing design guidance and external references converge on larger controls and keyboard alternatives for tiny click targets. Current design-spec hit-area guidance is 32px minimum and 40px preferred in selected mobile controls.

### Gaps a project-wide document could close

1. **Declare scope and target.** Distinguish RSS Dashboard-owned UI from Obsidian-host UI and embedded third-party article content. Decide and name any WCAG version/level target; state boundaries and avoid claiming conformance from unit tests or an automated scan alone.
2. **Establish one source of truth.** Reconcile the `title` exception and legacy `div[role=button]` recipe with the newer native-button direction. Point `.instructions.md`, the design spec, and test guidance at a single accessibility declaration or shared contributor section.
3. **Define minimum interaction expectations across surfaces.** Extend the design-spec examples beyond navigation and icon buttons to forms, menus/popups, dialogs, dynamic updates/status announcements, empty/error/loading states, zoom/reflow, reduced motion, forced colors, and screen-reader checks where the plugin owns the markup.
4. **Make verification coverage explicit.** Separate static/lint checks, jsdom behavior assertions, runtime CDP/accessibility-tree checks, screenshot review, and manual keyboard/screen-reader checks. Record what each does not detect; scan interactive states after opening them.
5. **State the bot-testing contract.** Prefer stable role/name/state and keyboard pathways for UI automation. Use test IDs only as a secondary explicit test contract where semantics cannot uniquely distinguish an element. Document which CDP/port path is supported by the test harness and preserve screenshots for visual evidence.
6. **Track known gaps and feedback.** Add a way for users to report barriers, identify who maintains the scope document, and review it when Obsidian APIs or plugin surfaces change.

### Rollout priority adopted after the research

The accepted plan avoids a standalone full inventory or usage analytics phase. Address clear severe barriers while improving reusable patterns and important workflows. Use current coverage as a risk signal, not a reason to delay broad, practical improvements.

1. During normal work, make a lightweight pass over dashboard navigation and article actions, Reader controls, settings/forms, dialogs, and keyboard-opened menus. These are plausible flows from the plugin's architecture, not analytics-verified traffic rankings.
2. Improve reusable control patterns (native controls, names, states, focus, keyboard activation) and fix severe barriers as they are encountered.
3. Extend those improvements across relevant themes, desktop/mobile/popout contexts, and empty/loading/error/expanded states without requiring an exhaustive one-time audit first.
4. Track verified checks, unknown combinations, and host/platform boundaries as coverage expands.

For the rollout's automation layer, the source-supported direction is: assert user-visible outcomes through resilient semantic locators where available; inspect the accessibility tree through CDP for runtime role/name/state; use screenshots for visual claims; and reserve manual keyboard/screen-reader review for issues automation cannot prove. A test ID or custom machine action can help bots, but should supplement the accessible user interface rather than conceal missing semantics.
